2. MIDI IMPLEMENTATION DEPTH
   ────────────────────────────────────────────────────────────────────────
   
   MidiClockOut (175 lines):
     • Sends 24 PPQN clock ticks every 16ms scheduling window
     • Stateless relative to AudioContext (no setInterval/setTimeout drift)
     • Integrated into AudioEngine._schedule() main loop
     • Supports Start/Stop/Continue/Song Position Pointer
   
   MidiNoteOut (320 lines):
     • Per-part configuration map (note, channel, duration)
     • Retrigger protection (cancels pending Note-Off before new Note-On)
     • Stuck note prevention (flush all Note-Offs on disable)
     • Local vs. external sound layering toggle
   
   useMidi Hook (1200+ lines):
     • Device enumeration + persistent selection (localStorage)
     • CC mapping to 140+ app actions (bpm, volume, pattern, fx, etc.)
     • Auto-learn with sequential CC+Note queue
     • 13 hardware presets with round-trip JSON import/export
     • Separate routing: clock-out device ≠ note-out device ≠ feedback device
     • Clock sync (receive external MIDI clock, sync BPM)
   
   → Implication: Highly sophisticated MIDI implementation; good foundation


3. AUDIO ENGINE ARCHITECTURE
   ────────────────────────────────────────────────────────────────────────
   
   Singleton pattern:
     • AudioEngine = new AudioEngineClass() (global singleton)
     • Scheduling loop: _schedule() called every 16ms (100ms lookahead)
     • Per-channel FX chain: Filter → Distortion → Compressor → Delay → Reverb
   
   MIDI integration points (lines 474, 482, 816, 1214-1267):
     • _midiClockOut: MidiClockOut instance (dependency injected)
     • _midiNoteOut: MidiNoteOut instance (dependency injected)
     • _midiOutCallback: legacy callback for custom MIDI processing
     • Public API: setMidiClockOutSender(), setMidiNoteOutSender(), etc.
   
   Scheduling:
     • play() → _midiClockOut.start()
     • _schedule() → _midiClockOut.scheduleTicks()
     • _scheduleStep() → _midiNoteOut.triggerNote()
   
   → Implication: Clean integration points; ready for OmniTribe protocol


4. ELECTRON INFRASTRUCTURE
   ────────────────────────────────────────────────────────────────────────
   
   Main process (electron/main.ts):
     • Window lifecycle management (BrowserWindow)
     • IPC handlers (ipcMain.handle, ipcMain.on)

   IPC patterns:
     • useElectron() hook (renderer → main, with browser fallbacks)

   Existing feature: WebSocket relay (collab-server.ts)
     • Shows pattern for device ↔ host bidirectional sync
   
   → Implication: USB/serial IPC layer can be built following collab-server pattern


5. BROWSER FALLBACK STRATEGY
   ────────────────────────────────────────────────────────────────────────
   
   Isomorphic design:
     • All components check useElectron().isElectron before native calls
     • Browser version works fully (minus file dialogs, native menus)
     • Pattern can be extended: if not Electron, try WebUSB / Web Serial
   
   Limitations:
     • WebUSB: HTTPS only, user must grant permission, limited to Chrome/Edge
     • Web Serial: HTTPS only, same permission model, better generic USB support
     • MIDI fallback: Full Web MIDI API works in all modern browsers
   
   → Implication: Browser support requires WebUSB + Web Serial polyfills


6. STATE MANAGEMENT PATTERN

   Implication:

================================================================================
                      RECOMMENDED APPROACH
================================================================================

1. PROTOCOL CHOICE
   • Custom binary (not MIDI class) for bandwidth efficiency + bidirectional sync
   • Frame format: [SoF 0xA5] [Len LE16] [Type u8] [Payload...] [CRC8]
   • Message types: ~20 enum values (HELLO, CLOCK_TICK, PATTERN_DATA, etc.)
   • Rationale: Standard MIDI is 3-byte packets; OmniTribe needs patterns (512+ bytes)

2. TRANSPORT LAYER
   Electron:
     • Native USB library (npm: usb, serialport)
     • OmniTribeBridge class (abstraction over USB I/O)
     • Electron IPC handlers (omnitribe-ipc.ts) → renderer
   
   Browser:
     • WebUSB API (navigator.usb.requestDevice())
     • Web Serial API (navigator.serial.requestPort())
     • Same Bridge interface, different backend

3. INTEGRATION PATH
   Week 1-2:  USB enumeration, connection, handshake
   Week 3:    Clock sync (START/STOP/TICK)
   Week 4:    Pattern + sound sync (bidirectional)
   Week 5:    Hardware button/encoder feedback
   Week 6:    Browser fallback (WebUSB/Serial) + testing

================================================================================
                         CRITICAL INSIGHTS
================================================================================

1. MIDI ARCHITECTURE IS SOPHISTICATED
   SynthStudio's existing MIDI implementation (MidiClockOut, MidiNoteOut, useMidi)
   is production-grade and directly applicable to OmniTribe. The dependency
   injection pattern makes it testable without hardware.

2. CUSTOM PROTOCOL RECOMMENDED (NOT MIDI)
   Standard MIDI (24 PPQN clock + note messages) cannot efficiently sync patterns
   (256+ bytes bidirectional). A custom binary protocol with message framing is
   necessary for OmniTribe's full feature set.

3. ELECTRON + BROWSER DUAL PATH
   SynthStudio's isomorphic design (useElectron hook with browser fallbacks) means
   OmniTribe can be implemented for both desktop (native USB) and browser (WebUSB)
   with parallel code paths.

4. TESTING IS STRAIGHTFORWARD
   Dependency injection + mock device + Vitest make integration testing simple
   without real hardware (critical for CI/CD).

5. KORG KNOWLEDGE ALREADY IN CODEBASE
   Electribe 2 format parsers exist (ESX-1, E2S). Parameter encoding for OmniTribe
   can reuse this domain knowledge.
